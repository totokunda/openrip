# Decoder benchmarks — 2026-10-16

`openrip-dev decode-bench <file>` (add `--ffmpeg-hw` for FFmpeg's VideoToolbox hwaccel). Apple M2 Max, macOS, FFmpeg 9.0.2. Seeks are frame-accurate (verified frame-by-frame in `engine/crates/media/tests`). Random seeks: 60 deterministic pseudo-random times across the file.

**CapCut column:** not measured yet. CapCut's logs are encrypted, so its seek latency needs an external screen-capture measurement (method in [../capcut-decode.md](../capcut-decode.md#measuring-capcut)).

## Notes

- **Why native is 3–4× faster:** FFmpeg's VideoToolbox hwaccel submits one frame and waits for it. The native path keeps up to 16 frames in flight and doesn't output frames a seek only needs as references.
- **Open cost.** The first VideoToolbox session in a process costs about 81 ms; after that, opening a decoder takes about 2 ms and its first frame arrives at about 8 ms (FFmpeg's path: 14 ms). `openrip_media::warm_up()` pays that first cost on a background thread at engine start. The playback layer should still pre-open and pre-seek the next clip, as CapCut does.
- The phone clips are local media and not in the repo. The 4K60/8K30 files are `testsrc2` encodes made with the commands in [spikes/frame-transport/README.md](../../../spikes/frame-transport/README.md).

## Scrubbing (`openrip-dev scrub-bench`)

`openrip-playback`'s `FrameServer` under a simulated playhead drag: 120 Hz requests for 2 s, newest request wins.
- **Scrub mode:** a cached frame within the tolerance; otherwise the exact frame if no seek is needed; otherwise the GOP's keyframe if it is close enough. The tolerance is 50 ms of drag.
- **Accurate:** always the exact frame.
- **Measures:** frames shown per second (max 120), the request-to-frame delay, and the time to the exact frame after release ("settle").

| Clip | Drag speed | Scrub: shown/s, delay p50/p95 | Accurate: shown/s, delay p50/p95 |
|---|---|---|---|
| 4K30 H.264 phone clip | 1× | 118, 0 / 6 ms | 118, 0 / 4 ms |
| | 16× | 62, 2 / 45 ms (settle 35 ms) | 73, 16 / 33 ms |
| 1080p HEVC 10-bit | 16× | 100, 0 / 31 ms | 120, 2 / 3 ms |
| 4K60 HEVC | 16× | **120, 0 / 5 ms** | 82, 16 / 23 ms |
| 8K30 HEVC | 16× | **120, 0 / 11 ms** (settle 84 ms) | 22, 47 / 90 ms |

Scrub mode pays off where decoding can't keep up with the drag (8K, fast drags over 4K). Elsewhere it matches accurate-only mode. The UI should widen the tolerance only when the drag is fast, as CapCut does.

## Decode + composite into the preview surface (`openrip-dev play-bench`)

Every frame is decoded on the native VideoToolbox path, then composited by `openrip-render` into an IOSurface-backed 1920×1080 BGRA pixel buffer: GPU YUV→RGB, CapCut's sharpened area downscale, Catmull-Rom placement. That buffer is what the app hands to Electron's `sharedTexture`. Each frame waits for the GPU (not pipelined yet). CPU is this process only, so there is no UI and no audio.

| Source → 1080p preview | Throughput | Decode / composite per frame (p50) | CPU at real time (estimated) |
|---|---|---|---|
| 4K60 HEVC | 186 fps (3.1× real time) | 0.3 / 5.0 ms | ~19% of one core |
| 4K30 H.264 phone clip | 194 fps (6.5×) | 0.5 / 4.4 ms | ~8% |
| 8K30 HEVC | 64 fps (2.1×) | 0.6 / 14.8 ms | ~29% |

**CapCut column:** in the earlier whole-app head-to-head ([2026-10-15](2026-10-15-playback-4k60.md)), CapCut used 48–70% CPU playing 4K60. That covers its whole app, including UI and audio. The like-for-like comparison comes once the engine drives the app preview.

## Playing a real multi-cut draft (`openrip-dev playthrough`)

A 107 s portrait draft, rendered frame by frame at 540×940 the way playback does: 31 video clips (14 H.264, 1 ProRes 422 HQ 1440×2560), 33 text clips.

| | Before | After |
|---|---|---|
| All frames | p50 34.2 / p95 42.4 ms | **p50 2.9 / p95 7.3 ms** |
| Frames where a clip starts | p50 39.6 / max 46.3 ms | p50 5.6 / max 8.3 ms |
| Frames over the 60 fps budget | 6,455 of 6,455 | 2 (the first is GPU warm-up) |

**Why it was slow:** ProRes decodes on VideoToolbox through FFmpeg into 4:2:2 biplanar 10-bit (P210), which the GPU import didn't take. Every frame went through swscale on the CPU instead. P210 now goes to the GPU without a copy too.

**A colour bug found on the way:** the CPU path for those frames lost the frame's range, so ProRes previewed desaturated.

## Cuts and prefetch

`PreviewEngine` prefetches. A background thread opens and positions the decoder for every clip starting within the next 1.5 s, and decodes upcoming stills. It hands them to the render thread, which waits for a prefetch already in flight rather than duplicating it. `openrip-dev playthrough --realtime` paces frames like real playback.

On the 17 local drafts whose media is present, paced at real time, frames where a clip starts render within 13 ms. One draft (4K phone clips) went from 12 frames over the 60 fps budget in 20 s to 2: the GPU and decoder warm-up on frame 0, and one stall described below.

**Known:** about once per 20 s run, a single decode blocks around 100 ms inside VideoToolbox's out-of-process decoder (`RemoteVideoDecoder_DecodeFrameWithOptions` waiting on a semaphore). Shrinking our frame cache moves the stall later but doesn't remove it, so it looks like the decoder service growing its buffer pool. The next thing to try is decoding ahead of the playhead, so one slow decode doesn't land on a displayed frame. `OPENRIP_TRACE=1` logs slow layers, decoder seeks and reads, and VideoToolbox waits.

## Render-ahead preview pipeline (`openrip-dev pipeline-bench`)

`PreviewPipeline` renders frames ahead of the clock (4 frame times) on a worker thread into a pool of IOSurfaces; each display refresh takes the newest frame due. Simulated 60 Hz display, wall clock, 540 px, 20 s of each of the three hardest local drafts:

| Draft | Frames shown | Late (> 1 frame) | Dropped | Longest gap without a new frame |
|---|---|---|---|---|
| 4K phone clips, 24 fps | 480 of 480 | 0 | 0 | 57.9 ms (one frame + one refresh) |
| 30 fps draft | 600 of 600 | 0 | 0 | 41.2 ms |
| 24 fps draft | 480 of 480 | 0 | 0 | 57.1 ms |

The ~100 ms VideoToolbox stall above no longer reaches the screen: render-ahead absorbs it.

## Timeline thumbnails (`openrip-dev thumbs-bench`)

40 thumbnails 64 px tall spread over the whole file. Quick = one keyframe decoded per GOP and shown for every time in it; exact = the frame at each time. The first thumbnail of a run includes opening the decoder (and, in a fresh process, the first VideoToolbox session).

| Clip | Quick, all 40 | Exact, all 40 | Exact again from the disk cache |
|---|---|---|---|
| 4K60 HEVC, 60 s (12-frame GOP) | 319 ms (8.0 each) | 495 ms (12.4 each) | 3.8 ms |
| 8K30 HEVC, 10 s | 511 ms (12.8 each) | 1,754 ms (43.9 each) | 3.4 ms |

**Why the first version was twice as slow:** the GPU area filter loops over each output pixel's footprint. From 4K down to 64 px, that is about 1,000 reads per pixel on only 7,000 threads: 9 ms a frame, against 1.4 ms for a 540p preview. The thumbnailer now stops the GPU at up to 6× reduction and finishes with an exact box filter on the CPU.

Quick only beats exact by a wide margin on long GOPs (phone and camera footage, 1–2 s), where many thumbnails share a keyframe. With 12-frame GOPs, every thumbnail has its own.

## Fewer GPU allocations per frame

The compositor allocated new intermediate textures every frame, including a full-resolution RGBA texture for each video frame (33 MB at 4K), plus a new readback buffer. They now come from a pool, freed after three frames unused.

Playthrough at 540 px, 20 s, p50 before → after: 4.3 → 3.8, 2.8 → 2.5, 6.9 → 6.6, 4.5 → 3.8, 5.2 → 4.1 ms (the five heaviest local drafts).

## Missing media no longer stalls a cut

The prefetcher dropped failed jobs without a word. When a clip's or still's file was missing, a render that waited for its prefetch sat out the whole 500 ms timeout, twice when two were missing. Failures are reported now. On the eight drafts that showed it, the worst frame went from 510–1,035 ms to 9–124 ms; the 124 ms is GPU warm-up on frame 0.

## Waveforms (`waveform` in the addon)

Peak and RMS per 10 ms of the mono mix, from the clip's own file. A 46 s 1080p screen recording with AAC: 92 ms to decode (230 ms before the decoders stopped reading the other streams' packets, see below), 0.4 ms from the disk cache. A 16.6 s phone clip: 88 ms, then 0.1 ms.

**Both decoders now skip the other streams' packets.** The audio decoder used to read every video packet of a clip off the disk and throw it away, and the video decoder every audio packet. Playback's mixer reads audio from video files all the time, so this also takes a clip's video bitrate (up to 100 Mbit/s for 4K phone footage) off the disk while playing.
