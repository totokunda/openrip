# 2026-10-15 — 4K60 HEVC playback cost

- **Machine:** Apple M2 Max, macOS 27, 4K external display. Background load was present during both runs (a QEMU VM at 40–100% CPU), so **system-wide GPU numbers are noisy**; CPU and memory are per-process and reliable.
- **Media:** `spikes/frame-transport/media/test-4k60-hevc-60s.mp4` (3840×2160, 60 fps, HEVC 60 Mb/s, AAC).
- **Method:** `node bench/sample-procs.mjs --decoder --delay 5 --seconds 15` (CPU from CPU-time deltas, 100% = one core; RSS summed across the app's processes; VideoToolbox decode service included). OpenRip was re-measured back to back with CapCut.

## Head-to-head

| | OpenRip spike (decode + display only) | CapCut 9.5.0 (playing in its editor) |
|---|---|---|
| CPU, % of one core (mean) | **37.4** (WebGPU canvas, moving playhead) | **70.0** |
| Memory (resident, all processes) | **490 MB** | **2,813 MB** |
| VideoToolbox decode service CPU | 3.0% | 8.2% |
| System GPU util (mean, noisy) | 23.4% | 6.1% |
| Dropped frames | 0 | not measurable from outside |

Fairness: CapCut is doing more (audio playback, its full timeline UI, its effect pipeline). This sets our floor, not a final win. The engine must stay below CapCut once it does the same work.

Raw data: [`2026-10-15-capcut-4k60.json`](2026-10-15-capcut-4k60.json), [`2026-10-15-openrip-spike-4k60-b2b.json`](2026-10-15-openrip-spike-4k60-b2b.json).

## Where OpenRip's cost goes: Chromium compositing

All at 4K60, 60 fps delivered and presented, zero drops:

| Presentation path | CPU (% of one core) | Chromium GPU process | Renderer |
|---|---|---|---|
| WebGPU canvas, static UI | 31.0–31.5 | 15.0 | 6.8 |
| WebGPU canvas, playhead moving every display refresh (120 Hz) | 37.4–40.8 | 19.8–21.2 | 8.5–9.6 |
| WebGPU canvas, playhead at 60 Hz (`will-change`) | 32.6 | 15.2 | 8.1 |
| `<video>` fed by `MediaStreamTrackGenerator`, static UI | 25.3 | 10.8 | 5.2 |
| `<video>`, playhead at 120 Hz | 38.6 | 18.4 | 9.9 |
| `<video>`, playhead at 60 Hz (`will-change`) | 28.4 | 12.3 | 6.4 |
| `<video>`, playhead at 30 Hz (`will-change`) | 29.5 | 12.7 | 7.0 |
| Native CALayer above the web UI, static UI | 11.3–12.0 | 1.5 | 1.9–2.1 |
| Native CALayer under a transparent web UI, static UI | 14.2 | 2.7 | 3.4 |

Findings:

1. **Handing frames to Chromium is nearly free** (under 1 ms per frame). The cost is Chromium compositing a 4K surface 60 times a second: about 20% of a core plus GPU work, versus about 2% when macOS shows the frame on a native layer.
2. **`<video>` presentation is cheaper than a WebGPU canvas** (25% vs 31% CPU, static UI). Chromium hands the video to its own OS-level layer.
3. **UI animation during playback is expensive.** A playhead moving at the display's 120 Hz adds 9–13 points of CPU. Capping UI updates to 60 Hz on a promoted layer recovers most of it. The editor's UI must follow an animation budget during playback.
4. **The native layer is the efficiency ceiling** (12% CPU total, Chromium almost idle). Its problem is layering: HTML can't draw on top unless the window is transparent, which costs more.

## Not valid / excluded

Runs where frames weren't actually displayed were discarded, rather than reported as wins: a harness bug on an Electron `loadFile()` quirk, and a shell variable that wasn't split into separate arguments. The harness now counts frames presented to the screen (`requestVideoFrameCallback`) for `<video>` runs, so a non-displaying run is detectable.
